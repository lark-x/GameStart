# AI 功能优先开发工作流

## 当前阶段

项目处于功能闭环优先期。AI 的默认任务是尽快让用户在实际页面完成一次可持久化的业务操作，而不是按内部模块拆分开发批次。`.ai/modules.json` 用于理解依赖方向，`docs/tasks/*.json` 仅保留历史记录。

## 用户只需要提供什么

描述希望看到的结果即可，不需要指定代码文件、模块、分支或验收矩阵。目标清楚时 AI 直接检查工作区并实现；只有产品语义不明确，或涉及破坏性 migration、数据删除、认证秘密、不可逆公共接口和真实生产副作用时才停下来确认。

## 可复用提示词

```text
阅读根 AGENTS.md 和当前功能直接相关的代码与文档，保护已有未提交改动。

任务目标：<用户可见结果>

围绕这个结果完成最短纵向闭环，可以在同一分支修改 Web、API、Worker、Contracts、Domain、Ports 和 Database。不要创建任务 JSON、Interface Request 或按模块拆分分支；不要为未出现的风险预建抽象、恢复分支和测试矩阵。

先让实际页面产生并读取持久数据，再补当前入口需要的加载、错误和失败处理。保持依赖方向，外部生成结果不得绕过审核写入 Canon、Release 或 Save。

完成后运行直接受影响模块的 typecheck、关键测试和一次实际用户路径。日常使用 pnpm verify:fast；只有 PR、发布或明确里程碑才运行 pnpm verify:release。报告真实执行结果，不把 Fake 当作真实外部服务验收。
```

## 分支与提交

- 分支和提交按用户结果组织，一个纵向功能可以跨多个内部模块。
- 不要求从最新 `main` 重建分支，不要求 stacked 分支、模块前缀、Interface Request 或先合并共享 Contract。
- AI 在用户明确要求时提交、推送或创建 PR；默认完成实现和验证，不擅自合并 main。
- 现有任务 JSON 和旧模块分支作为历史证据保留，不继续更新。

## 验证节奏

- 日常：受影响模块 typecheck、一个关键测试、一次实际页面路径。
- 具体高风险：只增加与破坏性 migration、秘密、不可逆接口或真实生产副作用直接相关的验证。
- PR、main、发布或明确里程碑：运行 boundaries、全仓 typecheck、测试、覆盖率、build、真实服务集成和 E2E。
- Fake、临时 SQLite、受控 HTTP 和真实外部服务分别报告，不让未配置的 Redis、LLM 或 ComfyUI 阻塞离线核心功能。

首个真实业务闭环必须通过实际 Web/API/Worker 创建非测试数据，完成候选审核、Canon 写入、生成任务回写，并在刷新和服务重启后保持一致。达到该节点后再单独制定轻量治理规则。
